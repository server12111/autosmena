# Проверка и исправления

## Исправленные ошибки

- Просрочка счёта могла перезаписать статус `paid` при одновременной обработке webhook. Обновление теперь условное, а регрессионный тест вставляет зачисление непосредственно перед SQL-запросом просрочки.
- Несколько одновременных запросов могли создать несколько активных счетов для одного клиента. Создание сериализовано по записи пользователя.
- Повторная одновременная корректировка баланса могла завершаться ошибкой уникальности. Повтор с тем же ключом и параметрами теперь успешно возвращается без второго зачисления.
- После сбоя создания счёт мог зависнуть в `creating`, а оплаченный внешний invoice было некуда привязать. Worker переводит зависшие создания на сверку; админка восстанавливает invoice только при совпадении ID, суммы, валюты и случайного payload. Платёж дополнительно должен быть подтверждён провайдером.
- При временном уменьшении счётчика SMS повторное значение приводило к конфликту уведомлений. Сохраняется максимум уже обработанного счётчика.
- Заказы старше последних десяти были недоступны в боте. Добавлены страницы заказов и пополнений; проверка конкретного заказа показывает именно его.
- Переход из ввода суммы к другим разделам не отменял режим ввода. Теперь навигация сбрасывает этот режим.
- Оплаченный или просроченный TON-счёт продолжал показывать инструкцию отправить перевод. Повторный призыв к оплате убран; просроченные HTTPS-счета также не показывают кнопку оплаты.
- Пустая фиксированная цена незаметно переключала расчёт на наценку. Теперь это ошибка ввода, а поле обязательно в соответствующем режиме.
- Админка сортировала заказы и пополнения по случайному UUID. Теперь сортировка идёт по времени создания с дополнительной стабильной сортировкой по ID.
- Неопределённое продление можно было только вернуть, даже если оно реально выполнено. Добавлен вариант завершения после явного подтверждения администратором и проверки действующего номера у поставщика, с записью в аудит и без изменения баланса.
- При смене режима доступа старый контейнер reverse proxy мог оставаться запущенным. Скрипт удаляет контейнеры, отсутствующие в новой конфигурации; тома БД не удаляются.
- Частичная неудачная резервная копия могла выглядеть как готовый dump. Готовое имя присваивается только после успешного `pg_dump`.

## Фильтр срока

Для новых и повторно используемых номеров задан только `expiry=5`, соответствующий выбранному пункту «Більше 60 днів». В переданной OpenAPI-схеме значение описано как 60–80 дней. Наличие проверяется с этим фильтром перед покупкой и при включении товара. Во время импорта ранее включённые товары без подходящих номеров отключаются. Продление ранее выданных номеров использует месячные периоды поставщика; ровно 60 суток API не гарантирует.

## Выполненные проверки

Проходят 111 тестов серверной части и 7 тестов интерфейса. Они проверяют конкурентные операции баланса, гонку оплаты и просрочки, принадлежность invoice, фильтр срока, уведомления, страницы бота и админку. Дополнительно проверены повторная и параллельная инициализация схемы, сохранение баланса между отдельными запусками, перенос незаписанного в основной файл WAL и сохранение пароля админки, ограничение каталога проектом Telegram США и резервный вывод обычных emoji при отказе Telegram принять premium-разметку.

## Постоянная база и настройки Bothost

- База автоматически размещается в `/app/data/smena.db`; новый `DATABASE_URL` или `DATA_DIR` задавать не нужно.
- `main.py` применяет миграции и запускает все три службы в одном контейнере. Раньше Dockerfile запускал только админку, поэтому при обычном одиночном контейнере бот и проверка платежей могли вообще не работать.
- Добавлены WAL, `synchronous=FULL`, ожидание блокировок и межпроцессная блокировка миграций.
- Исправлен перенос старой базы при наличии заранее созданного пустого файла назначения. Ранее такой пустой файл мог мешать обнаружению старых данных. Исходник сохраняется, рабочая база назначения не перезаписывается.
- При копировании SQLite соединения закрываются до переименования; это устраняет ошибку занятого файла на Windows.
- Если одна служба падает, супервизор завершает остальные, чтобы контейнер перезапустился целиком.
- В примерах осталось 6 полей с ключами и кошельком. Пароль админки создаётся автоматически и сохраняется; валюта поставщика настраивается в админке и хранится в БД.

## Что требует проверки на сервере

Локально выполнена одна реальная покупка Telegram США: списание api.cc составило 0.300, номер получил статус active. Telegram принял premium emoji в сообщении и кнопках, а также цветные кнопки. Ответ `/api/record` проверен на выданном номере: отсутствие кода обозначено `code=0`, данные содержат `code`, `code_time`, `expired_date`. Бот читает этот интерфейс на сервере без передачи ключа аккаунта и без переходов по redirect; код отправляет в чат, сохраняя аренду активной. Ссылки приёма скрыты, HTTP-логи с приватными URL отключены. Дедупликация по коду и времени сохраняется в БД; устаревший ответ не заменяет более свежий код. Успешный ответ с кодом проверен на HTTP-фикстурах; реальное входящее SMS нужно запросить в Telegram.

Контейнеры Docker и запуск на Bothost здесь не выполнялись. Реальные пополнения через TON / Crypto Bot / xRocket, повторное использование и продление требуют отдельных контрольных операций. Валюту кабинета api.cc нужно подтвердить при настройке в админке.

## Вебхуки

Добавлена очередь `webhook_events` с миграцией: webhook подтверждается только после сохранения, повторы объединяются по идентификатору события. Crypto Pay и xRocket Legacy проверяют HMAC по исходному телу запроса, Telegram — отдельный секретный заголовок. Тела ограничены по размеру до разбора. Платёжные события обрабатываются независимо от HTTP-запроса, с повтором после временных ошибок, обязательным чтением счёта через API и прежней идемпотентностью баланса. Подпись Legacy подтверждена официальным руководством миграции xRocket; недокументированный формат Legacy не используется для зачислений.

В админке появились HTTPS-домен, переключатель Telegram и адреса callback для Crypto Pay / xRocket. Настройки сохраняются в БД. Telegram регистрируется при следующем запуске; локально по умолчанию polling. При отключении webhook накопленные обновления не удаляются. События после сбоя возобновляются из очереди. Опрос SMS и TON сохранён; HTTP callbacks в переданной документации api.cc и текущем REST-подключении TON Center отсутствуют.

Проверены неверные подписи, повторные доставки, защита секретного заголовка Telegram, сохранение до ответа, однократное зачисление, повтор после ошибки провайдера, восстановление после перезапуска, CSRF настроек и сохранение через интерфейс. Настройка провайдеров и реальная доставка на HTTPS-домен снаружи ещё не выполнялись.

Crypto Pay: `update_id` официально указан как неуникальный. Ключ очереди для оплаты строится по `invoice_paid` и `invoice_id`, поэтому совпавшие update ID разных счетов не теряют события. Добавлен регрессионный тест на два счёта с одинаковым update ID и повторную доставку первого.
